## Release/version policy — owner's canonical `x.y.z.a` specification
**Target first release after implementation: `0.9.0.0`. The sole user-visible version must be `x.y.z.a` on `Settings → About` (Credits/About can remain a navigation entry, but must not display the version anywhere else).**

| Part | Meaning | Increment and examples |
|---|---|---|
| `x` | Complete product milestone | Stay at `0` throughout incomplete/alpha development. Set to `1` **only after all owner-agreed requirements have been implemented, tested and owner-accepted**; reset lower parts on major milestone. |
| `y` | Major game change / new feature | New LAN play, new Career mode capability or other new functional feature: e.g. `0.9.0.0 → 0.10.0.0`. Reset `z,a`. |
| `z` | Minor enhancement to an existing capability | Upgrade an existing feature, new animation pack, new ability pack, graphics overhaul increment: e.g. `0.9.0.0 → 0.9.1.0`. Reset `a`. |
| `a` | Bug fix, re-release, small corrective patch | Navigation Back fix, compatibility fix, emergency release: `0.9.0.0 → 0.9.0.1`. |

**Rules:** Four nonnegative integer components; do not confuse `0.9.0.0` with old `0.8.25.32` or an internal Git SHA. Advance **once per published player-facing game update** based on the highest-impact change included; independent docs/claim/checkpoint commits are not game releases. Record a one- or two-sentence *human-readable change summary* and a short dated release history alongside the new version in About. A bundled release can mention all shipped changes under one new number. The first future rollout migrates the visible version to `0.9.0.0` as requested; do not imply that this documentation-only update has already changed the game. Preserve exact immutable Git commit and deployed-asset SHA **internally for build/CI traceability**, never display the `+dev.7370...` or raw commit SHA as the normal user-facing version. About must reflect the **installed/deployed build**, not merely remote HEAD, and remain readable offline.

**Known policy conflict:** Current `docs/VERSIONING_POLICY.md`, root `AGENTS.md`, tests `about_revision.test.cjs`, `versioning_policy_contract.test.cjs`, page/menus and runtime presently require/display the `v<BUNDLE>+dev.<SHA>` convention. These **must be migrated together** under a properly approved `ui-controls` + `release-infra` + relevant `project-context` ownership plan. Do not remove SHA traceability from CI or falsely claim compliance while current tests enforce the old rule. A safe implementation needs a single release-authoritative `gameVersion`, offline/deployment-embedded revision manifest, release notes data, migration of visible strings and tests, and a serial release owner to prevent concurrent agents racing version numbers.

### Specific implementation sequence (bounded independent batches, not one giant rewrite)
1. **FIX-UI-101 + FIX-UI-102:** reproduce and repair Back flows, remove home `dev → About` banner, add cross-device navigation tests. A new version should only be published when the release-control system safely supports it; until then preserve source identity.
2. **VER-101 / 102 / 103:** coordinated `ui-controls`, `release-infra` and relevant context governance acceptance; implement embedded actual release version `0.9.0.0`, user-friendly About notes, **no public SHA** and migrate contracts/tests. Only release when exact-SHA QA/Pages and backup compatibility pass.
3. **SAVE-101 / SAVE-102 / SAVE-103:** first 10 Career slots, then 10 Cups slots, then lossless migration and reload stress tests.
4. **STUDIO-101 / 102 / 103:** player stats editor, then move-family chooser, then dribble types/preview. Preserve exactly four gameplay buttons.
5. **UX-101 / 102 + ART-101 / 102:** in parallel *under disjoint owned scopes*, progressively author real illustrated menus and enhanced eight-view player art/unique special animations. Owner signoff needed.
